# Source-of-Truth Validation

## Purpose
Protect the implementation from requirement drift.

## Invoke when
- interpreting a requirement;
- proposing architecture or scope changes;
- deciding whether a technology or feature is necessary.

## Review questions
- What does the task explicitly require?
- What is assumption versus requirement?
- Does the proposal materially improve requirement coverage?
- Has implementation complexity started redefining the problem?

## Evidence expected
- original requirement text;
- explicit assumptions;
- requirement-to-implementation mapping;
- documented limitations.

## Failure signal
A design decision cannot be traced back to a requirement, risk, or clearly stated assumption.
